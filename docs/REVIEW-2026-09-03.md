**Overall assessment.** The project has a strong multiplayer foundation and enough mechanics to support a distinctive game. Its next milestone should concentrate on reliable combat feedback, understandable builds, team/objective readability, and predictable match pacing. More cards and modes would increase the current interaction and maintenance problems before resolving them.

The strongest elements are server-owned combat and drafting, separation of most simulation data from scene nodes, deterministic testability, bounded projectile transport, shared map geometry, configurable bots, and an established visual palette. The weakest areas are simulation parity between online prediction/offline play/server truth, hidden limits on advertised card effects, and a presentation layer that communicates individual statistics better than tactical decisions.

**Prioritized defects and interaction gaps**

P1 means address before a wider competitive playtest. P2 means address in the next hardening/polish iteration. Items explicitly marked design gap or source risk need their intended behavior agreed before implementation.

**1. P1 — Respawn cleanup deletes projectiles from the new life. Confirmed by probe.**

`respawn_peer()` resets a ship and then schedules cleanup for its owner ID. Half a second later, the registry deletes every projectile belonging to that owner, including shots fired after respawning. A probe respawned a pilot, added a fresh projectile, advanced cleanup by 0.5 seconds, and observed that fresh projectile removed. This affects the three respawning objective modes and makes the first post-respawn volley unreliable.

Clean up the old life's projectiles before respawn, or associate deferred cleanup with projectile IDs/a life generation. Verify that old shots expire and fresh shots/mines/missiles survive according to their own rules.

Evidence: [respawn](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/authoritative_world.gd:177), [owner-wide cleanup](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/projectile_registry.gd:163).

**2. P1 — Afterburner prediction does not simulate the server's movement. Confirmed by probe.**

The server applies Afterburner duration, speed multiplier, and acceleration multiplier. Client prediction always passes a speed multiplier of 1.0 and does not replay Afterburner state. The world view adds an initial impulse outside the prediction buffer, so reconciliation cannot reproduce that activation either. Starting both simulations with the same active boost and velocity produced 61 pixels of separation after 300 ms: server speed 792 versus predicted speed 480. This measures simulation divergence without intervening snapshots, not a measured 61-pixel live visual jump.

Make movement-affecting ability state part of prediction and replay. Also cover shield depletion and Breakaway transitions: prediction currently uses requested shielding and a current Breakaway boolean, rather than the historical state for each replayed frame. Test at representative latency and around activation/depletion boundaries.

Evidence: [prediction motion](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/network/client_prediction_buffer.gd:83), [client activation](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/network/network_world_view.gd:270), [server combatant movement](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/combatant_state.gd:100).

**3. P1 — A stale input can keep firing or reactivate consumable specials. Confirmed by probe.**

The authority retains the latest input indefinitely and evaluates its special flag every tick. Cloak has an activation latch; Afterburner, mines, and missiles use cooldowns without equivalent action deduplication. One accepted special packet, followed by no new input for about six seconds, spent all three mine charges in the probe. A temporary client stall or loss of neutral/release packets can therefore keep actions running until transport disconnection or fresh input arrives.

Track server receipt time and neutralize stale continuous controls after a deliberate grace period. Give one-shot specials an action sequence/ID, acknowledging and deduplicating retransmissions. Do not simply edge-detect the existing flag without accounting for its three-send reliability scheme.

Evidence: [world input consumption](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/authoritative_world.gd:85), [special retransmission](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/network/network_world_view.gd:233), [input RPC](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/network/network_bridge.gd:809).

**4. P2 — Fire-rate upgrades have invisible plateaus. Confirmed by probe.**

Cooldown subtraction clamps away fractional overshoot; firing resets the timer to a whole new interval. At 60 Hz, requested rates of 15, 16, and 19 all yielded 15 shots/second. A request of 20 yielded 20. The probe replenished ammunition to isolate cadence. The practical rate is approximately `60 / ceil(60 / requested_rate)`, so some incremental fire-rate upgrades do nothing and later upgrades cause a sudden jump.

Carry fractional timing remainder or schedule shots against simulation time, while preserving intentional first-shot and reload behavior. Verify long-run cadence across intermediate rates, not just the base rate and clamp maximum.

Evidence: [weapon timer](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/weapon_state.gd:19).

**5. P1 — Unlimited acquisition can produce upgrades with only drawbacks. Confirmed design/feedback gap.**

Inventory stacks are unlimited, but effective stats are tightly capped: six projectiles, 20 shots/second, 600 hull, and other limits. Five Twin Shot stacks already produce six projectiles. A sixth keeps six projectiles, lowers per-projectile damage from 4.20175 to 2.941225, and increases spread from 50 to 60 degrees. The offer remains eligible and its preview still presents the card's nominal stacked modifiers. It does not show the actual before/after build after all cards and clamps.

Preserve unlimited card ownership while displaying derived before/after values and explicit saturation. Consider an overflow benefit or a clearly communicated balancing rule where appropriate. Raising caps blindly would worsen projectile budgets and encoding limits. Audit attainable combinations of different cards, not just high counts of one card. This also gives the draft UI a much more useful job than showing nominal rarity odds.

Evidence: [effective clamps](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/cards/stat_system.gd:127), [preview calculations](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/ui/card_hover_button.gd:110), [unconditional repeat eligibility](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/cards/card_catalog.gd:193).

**6. P1 — Overtime does not guarantee a heat ends. Confirmed liveness/design gap.**

Overtime stops shrinking at a positive radius and only damages players outside it. The probe found multiple legal, non-overlapping grid positions with zero overtime damage at an elapsed hour on eight of ten maps. Two passive pilots can occupy such positions indefinitely. Core Arena and Solar Tide returned no safe grid points in this sample because central cover occupies the sampled region; overtime behavior therefore also differs materially by map. This was a positional/logic check, not an hour-long playtest.

Objective modes add another route to indefinite play: respawns continue during overtime and there is no terminal heat deadline. In flag modes, the shrinking safe region is centered on the arena while scoring bases remain near its edges, increasingly penalizing the trip required to win.

Define terminal rules per mode: a hard deadline and tie resolution, final sudden death, an overtime objective, or a deliberate respawn cutoff. Test all maps, contested hills, passive pilots, all players dead, and flag-carrying routes. Avoid resolving objective ties by an undocumented arbitrary peer order.

Evidence: [overtime damage](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/overtime_system.gd:63), [respawn loop](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/match/authoritative_match_coordinator.gd:491), [flag scoring](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/match/authoritative_match_coordinator.gd:603).

**7. P2 — Respawn placement checks occupancy, not danger. Source-confirmed design gap.**

The preferred spawn is reused whenever another living ship is more than 60 pixels away and the geometry is clear. It does not assess enemies' firing lanes, armed mines, nearby projectiles, or overtime damage. No spawn-protection state exists in the combatant model. A legal spawn can therefore be tactically unsafe, especially late in objective heats.

Score a bounded set of candidates using enemy/projectile proximity, line of sight, and the current safe region. If adding protection, make its expiry visible and define whether attacking or touching an objective ends it. Validate spawn camping and repeated overtime deaths with actual matches before choosing durations.

Evidence: [spawn selection](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/match/authoritative_match_coordinator.gd:522).

**8. P1 — Team allegiance is not a dependable combat visual. Source and visual finding.**

Ship colour/pattern is personal identity. Projectile colour is selected from weapon-card rarity; shield colour is selected from shield-card rarity. None is a reliable indication of whether an entity is friendly. Offscreen ship markers likewise use personal colour and one of three identity marks. Team names in rosters and scoreboards do not resolve the moment-to-moment question of whom to shoot or dodge.

Keep personal hull customization, then add a separate allegiance layer: team crest/number, consistent ally/enemy outline or nameplate badge, and different friendly/hostile projectile treatment. Use shape as well as colour. Preserve stronger contrast for hostile threats and the local pilot. Validate the system in grayscale and with eight teams, not just a cyan-versus-magenta fixture.

Evidence: [ship appearance](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/network/network_world_view.gd:1246), [projectile palette](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/sandbox/sandbox_projectile_layer.gd:13), [offscreen markers](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/presentation/offscreen_indicator_layer.gd:25).

**9. P2 — Weapon state cannot be fully corrected from snapshots. Source risk; player-visible scenario needs targeted integration validation.**

Snapshots contain ammunition but omit reload progress, fire cooldown, and shot sequence. The client corrects ammunition while its separate `local_weapon` continues its own timers. Respawn resets the ship's presentation weapon but does not reset that separate local predictor in the snapshot path. A death during a long reload or a lost reload input can leave the HUD/predicted firing inconsistent with the server until local timing catches up.

Include the minimal authoritative weapon timing/state required for correction, and explicitly reset/reconcile the local weapon at respawn. Test dying mid-reload, manual reload under packet loss, and mid-heat magazine/reload upgrades.

Evidence: [snapshot record](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/network/player_snapshot_codec.gd:74), [snapshot application](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/network/network_world_view.gd:330), [resource reset](C:/Users/Graphite/Documents/code/SuperStarFighter/src/client/network/network_world_view.gd:571).

**10. P2 — Cloak is a rendering rule, not protected hidden information. Source-confirmed architecture boundary.**

The server encodes one complete player-state body and sends it to every human, including exact cloaked positions and velocities. Ordinary clients hide the ship, but a modified client still receives its location. Separately, NPC target selection ignores cloaked pilots while missile acquisition/guidance does not check cloak. These are two distinct decisions: network secrecy and whether homing weapons counter invisibility.

For trusted friend matches this can be an accepted limitation. Before presenting cloak as competitively secret, implement recipient-aware visibility with explicit reveal/despawn/reappearance behavior. Decide and document cloak interaction with missiles, mines, the flag, and hill occupancy. Do not accidentally remove an intended counter mechanic while fixing visibility.

Evidence: [shared snapshot body](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/network/network_bridge.gd:1435), [missile acquisition](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/authoritative_world.gd:392), [NPC targeting](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/npc_pilot_controller.gd:511).

**11. P2 — Uncollected powerups have no lifetime or population cap. Source-confirmed growth risk.**

Powerups continue spawning until the heat ends, remain in a dictionary until collected, and are sorted/scanned against players each simulation step. In an indefinitely stalled heat, a five-second interval can add 720 entries per hour before collections. They can also spawn outside the current overtime safe region because placement does not consume overtime state.

Add a small active-drop budget, expiry/replacement rules, and safe-region-aware placement. Keep these visible and deterministic. This is a secondary performance risk amplified by the missing terminal heat rule, not a measured memory leak.

Evidence: [spawn storage](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/card_powerup_system.gd:72), [collection scan](C:/Users/Graphite/Documents/code/SuperStarFighter/src/shared/combat/card_powerup_system.gd:88).

| State representation | Dictionaries are practical at serialization boundaries, but repeating string keys across simulation and UI hides schema drift. Use typed local event/state objects for frequently edited contracts, with explicit conversion to transport dictionaries. |
| Documentation | README advertises 2,815 assertions/93 checks; the development guide contains 2,923 and differing gate counts, and protocol 22 versus current code 24. The rarity audit's latest catalog count is 135 versus 136 resources. Generate current counts/version tables from code or label old evidence with dates. Separate delivered map rotation from the future roadmap in `maps.md`. |

Production drawing classes currently live under `sandbox/`, even when the online game depends on them. Rename/move these to a shared presentation location as part of extraction; the offline lab should be one consumer. Keep the simple RefCounted simulation and current resource-based cards. There is no evidence that an ECS rewrite, engine migration, or wholesale language rewrite is justified.

**Performance and resource use**

| Benchmark on this machine | p50 | p95 | p99 | Maximum |
| --- | ---: | ---: | ---: | ---: |
| 32 Insane NPCs / 1,024 projectiles | 15.440 ms | 17.064 ms | 19.371 ms | 23.809 ms |
| 512 mines / 512 moving projectiles | 10.282 ms | 10.997 ms | 15.079 ms | 16.516 ms |

The configured overload gate allows 20 ms p95 in the first case, so this is a pass. It does not establish a stable 60 Hz release server: 60 Hz provides about 16.67 ms, and this fixture times NPC decisions plus world simulation, excluding match coordination, encoding, fan-out, and client rendering. It samples 120 measured ticks after 20 warmup ticks on the default map. A release-mode, full-server soak remains necessary.

The benchmark's average phase breakdown was approximately 10.69 ms projectile work, 2.32 ms NPC decisions, 1.78 ms cleanup/threat-index work, 0.33 ms movement, and 0.21 ms overlaps. Optimize projectile work first. The spatial index, cached obstacle geometry, owner queues, reused snapshot body, and revision-driven UI rows are already worthwhile optimizations.

Recommended work, ordered by evidence:

1. Profile projectile collision subphases and temporary allocations on the most expensive maps, then reduce allocations/candidate work where measured. Inspect linear removal deduplication and reflected-projectile update scans under churn. Keep collision correctness as a gate.
2. Include actual coordination/serialization/fan-out in performance acceptance. At 32 players, the 35-byte player record plus 10-byte header is 1,130 bytes; at 20 Hz to 32 humans, player snapshots alone are about 723 KB/s outbound payload, excluding ENet overhead and projectile traffic. Budget and report these separately.
3. Separate static arena drawing from animated objective/overtime layers. `SandboxArena._draw()` redraws stars, grid, and cover whenever its animated objective/overtime queues a redraw. Static drawing can remain cached while only dynamic overlays update. Measure GPU/draw-call impact before batching all visuals.
4. Budget presentation effects at 32 players: hostile projectiles, the local ship, hit feedback, and objectives should survive effect reduction. Test with mines, beams, shields, and Afterburner together; two-ship screenshots do not establish crowd readability or frame time.
5. Review the projectile eviction policy as gameplay, not only optimization. All weapon forms share the per-owner 64/global 1,024 budgets, so new bullets can evict deployed mines or shorten a long-range build's effective projectile lifetime. Consider separate persistent-ordnance reservations and expose saturation. At six projectiles × 20 shots/second, 64 slots represent only about 0.53 seconds of unconstrained continuous output before evictions, absent hits/reloads.
6. Cache immutable sorted card IDs/rarity buckets and avoid rebuilding full stat/catalog views where revisions already identify changes. This is secondary to measured projectile work.
7. Music source WAVs total about 126 MiB and the audio director loads all gameplay tracks at startup. Import settings already enable compression, so source size is not runtime memory usage. Measure packaged audio size, startup latency, and resident memory before choosing streamed compressed music or lazy loading. Keep short effects preloaded.

**Graphical design language**

The navy surfaces, cyan/magenta accents, consistent rounded panels, amber focus treatment, and non-colour ship patterns form a coherent identity. Keep them. Main controls generally fit and the match-options modal is understandable. The game currently looks like a polished geometric prototype: its distinction comes mostly from palette, outlines, and text rather than a recognizable set of ships, weapons, and environmental materials.

| Gap | Concrete direction |
| --- | --- |
| Small type | Combat labels use 14–17 virtual-pixel fonts; at 720p these are roughly 9–11 physical pixels. Card metadata and preview rows are similarly small. Add text/HUD scaling and establish physical-size minimums for actionable text. Keep secondary details in a dedicated panel. |
| Competing borders | Panels, cards, obstacles, shields, pickups, and feed entries all use bright outlines. Reduce stationary-world emphasis; reserve the strongest luminance and motion for the current decision and immediate threats. |
| Team recognition | Add the independent allegiance grammar described in finding 8. Personal colours and rarity colours cannot carry this role reliably. |
| Objective ownership | An occupied hill turns green regardless of who controls it. Pair neutral/contested/self/enemy state with explicit text or symbols and a control-progress arc. Differentiate hill, pickup, shield, and overtime circles by stroke pattern and symbol. |
| Flag navigation | Solo bases are all labeled `PILOT BASE`; offscreen indicators cover nearby ships and an incoming projectile, not the player's base/flag/hill. Add an unmistakable `YOUR BASE` marker, owner labels, and objective direction/distance cues. |
| Ultrawide HUD | At 32:9, critical health information stays at the extreme left while the pilot is central. Offer a constrained HUD safe area independent of world width. Decide whether extra horizontal combat visibility is an accepted casual advantage or needs a competitive viewport rule. |
| Draft composition | The five-card layout has large unused vertical space while effect text and metadata stay small. Use that space for a short role label, a mechanic icon, and two or three actual build deltas. Put probability detail in the preview. |
| Card identity | Most differentiation is wording and rarity colour; the preview has a category glyph. Give mechanic families recognizable icons first—multishot, piercing, ricochet, repair, burst, mine, cloak—before commissioning 136 unique illustrations. |
| Ship evolution | Builds change many numbers without a comparable hull silhouette change. Add restrained, readable attachments/trails for major archetypes; preserve hitbox clarity. Do not make every numeric stack another overlapping effect. |
| World identity | Layouts differ but use broadly the same solid rectangles/circles/grid. Introduce a small material and landmark vocabulary: cover panels, reactor masses, lane markings, boundaries. Decorative art must agree with collision and stay subordinate to threats. |
| Accessibility | Remapping/deadzones and identity patterns are good. Add reduced shake/flashes, text scale, stronger contrast options, and hold/toggle alternatives where suitable. Validate actual focus/tooltip behavior with keyboard/controller, rather than inferring it from focusable controls. |
| Menu hierarchy | The first view centers server discovery, with the combat lab as an alternate. Add a clear quick solo practice route and a short explanation of match structure. `PASSWORD` as a join-row action could be clearer as `JOIN` with a lock indicator. |
| Lobby density | At 720p only a few roster rows are visible while configuration occupies much of the panel. Separate host settings from the roster, preserve readiness summary, and make scrolling/which pilot is unready obvious. |
| Small copy issues | `ROUND WINNER BUY` should be `BYE` or, preferably, `ROUND WINNER — SKIPS THIS DRAFT`. Avoid shorthand such as `OT` in the novice-facing default HUD. |

The rendered fixture places a powerup on the hill, exposing how easily its labels overlap the objective. This is a useful layout stress case, not proof that production spawning selects that exact overlap. Likewise, the preview capture is manually positioned by the harness; it does not establish live tooltip placement or controller navigation.

**Gameplay depth, onboarding, and balance**

The existing loop has meaningful choices: aim versus movement, firing versus shielding, reload timing, perfect guard, shield rams, ricochets, piercing, beam transformations, escape tools, drafting, and objectives. The most valuable missing mechanics are those that help players understand and deliberately combine these choices.

| Priority | Opportunity | Why it matters / acceptance idea |
| --- | --- | --- |
| First | Guided combat introduction | Teach Relative/Newtonian movement, shield arc and firing exclusion, manual reload, perfect guard, then one draft choice. A first-time player should finish a short exercise without opening the manual. |
| First | A usable build laboratory | The existing lab is valuable but relies on developer-style hotkeys and a separate simulation. Add searchable cards, archetype presets, reset, target controls, actual derived stats, and a shot/damage readout backed by the authority model. |
| First | Actual before/after draft comparison | Show effective damage, cadence, projectiles, reload, mobility, and relevant shield changes; call out unlocked mechanics and saturated benefits. This makes 136 cards manageable without removing variety. |
| First | Deliberate active-ability selection | One Special action currently activates every available Afterburner/mine/missile/cloak component. Escaping can spend ordnance and cloak together. Choose whether combo activation is intentional; otherwise support a compact selectable active slot or separate binds, with controller parity. |
| First | Clear hit/death explanation | Existing damage flashes and kill feed are useful. Add authoritative hit/block confirmation for the attacker and a short death recap identifying weapon/environment, killer, and relevant build. Help players distinguish a miss, a block, a network correction, and burst damage. |
| First | Mode-specific pacing | Resolve finding 6, then measure time to first contact, time dead, time drafting, and time to next round. A 32-player elimination heat and a duel need different pacing expectations. |
| Next | Objective team roles | Bots steer directly toward objectives and choose random draft cards. They lack build-aware drafting and explicit escort/defend/intercept roles. Objective steering also lacks a dedicated path around cover; existing flanking primarily addresses the combat target. Add simple roles and bounded waypoint/navigation support before more difficulty tiers. |
| Next | Spawn and comeback fairness | The winner's next-draft bye is already a comeback mechanic. Measure whether weaker pilots gain useful choices and whether permanent pickups create a countervailing snowball. Track win rate conditioned on build and pickups, not only rarity. |
| Next | Archetype support and counterplay | Tag cards by purpose and measure whether plausible builds can be assembled in ordinary match lengths. Test repair/sustain against burst, shield coverage against multishot, rams against mobility, and range against cover. A random high-rarity draw is not proof of a meaningful choice. |
| Next | Fast solo and party presets | Offer a few explained presets, such as duel practice, small skirmish, team objective, and chaos. Preserve advanced settings underneath. This reduces setup burden without deleting host controls. |
| Next | Rematch quality | Add an obvious same-rules rematch and concise results explaining objective contributions, not just kills/rounds. Distinguish extending the current escalating build from starting a fresh match. |
| Later | One signature arena mechanic | Destructible cover, a telegraphed movement field, or a relay can add routing choices. Build one with clear counterplay and shared simulation first. The roadmap's destructibles/fields/teleporters are not implemented merely because ten static maps exist. |

Death Match currently means last survivor, while the flag modes use one neutral flag and one return wins a heat. Those are legitimate rules, but names such as `Elimination` and `Neutral Flag` may teach expectations better. The hill moves between rounds, not continuously during a heat; its description should make that timing explicit.

Do not treat accounts, progression, a shop, ranked matchmaking, chat, or an expanded card catalog as prerequisites for making this version good. Reconnect restoration is more immediately valuable for long online matches, but requires an explicit authenticated participant-resumption design. Host migration and public matchmaking are larger separate projects. Basic pings could help objective coordination once ownership/navigation are readable.

Audio already has an authored music inventory, event deduplication, prioritized voices, distance attenuation, and weapon-family synthesis. The remaining audible polish needs listening tests: effect masking at 32 players, distinct shield/hull feedback, objective announcements, and whether direction is understandable. Current effect playback uses ordinary `AudioStreamPlayer` with volume falloff; consider spatial panning for nearby threats after evaluating the mix. Avoid adding more loud cues without priority/ducking rules.

**Verification gaps and release readiness**

The existing suite is a significant asset. Its 2,998 passing assertions nevertheless coexist with reproducible lifecycle and timing defects. Add tests at system boundaries rather than increasing counts with more constant/property assertions.

- Add regression coverage for findings 1–5, including activation retransmission and respawn generation changes.
- Add mode/map liveness scenarios with an explicit maximum test duration, all-dead objective states, final-circle occupancy, and scoring routes through overtime.
- Test real input under delayed/lost/reordered delivery; compare authoritative and predicted ability/weapon state, not just decoded packet fields.
- Add 32-player visual stress fixtures, full mixed builds, longest labels, all active abilities, objective modes, and actual controller focus traversal. Existing screenshot existence/size checks establish rendering, not readability.
- Benchmark the release server and rendered client independently on representative hardware, then a full match across expensive maps. Record p95/p99, over-budget ticks, bandwidth, memory trend, and visibility/effect counts.
- Automate export-content allowlisting: presets use `all_resources` with an empty exclusion filter, so test/development resources need deliberate packaging review. Preserve the server-only path and produce a stripped dedicated-server artifact when distribution becomes a priority.
- Complete clean-machine Windows testing, native Linux/macOS acceptance, signing/notarization as appropriate, and release-mode soak. Cross-build inspection is not native play validation.
- Establish source/asset licensing records and attribution inventory; the repository declares no project license and the notices file covers Godot. This is a release bookkeeping gap, not a finding that any bundled asset is unauthorized.

The best next deliverable is a focused correctness-and-readability build: reliable respawns and abilities, honest upgrade comparisons, unmistakable team/objective cues, and bounded match pacing. That would make the existing content substantially more valuable.
